# 懸賞Pocket — Codex用 本番実装設計書 v1.0

作成日: 2026-09-23 / 言語: 日本語 / 対象: 個人利用のAndroidアプリ

> このファイルは開発仕様であり、完成済みアプリ・APK・実機試験報告ではない。
> 記載した画面、初期値、上限、内部処理は本プロジェクトで採用する設計判断である。
> Android等の既存技術に関する根拠は `SOURCES.md` の公式資料を参照する。

## 1. 作るもの

LINE・X・Web等で見つけた懸賞を、共有／貼り付け／スクリーンショットから登録し、応募忘れと賞品の受取忘れを減らすAndroidアプリを作る。

中心となる流れ:

```text
文章・URL・画像を取り込む
  → 複数の懸賞を候補に分割
  → タイトル・URL・締切・応募周期を確認
  → 一覧に保存
  → 締切前／毎日の応募時刻に通知
  → ボタン一つで応募ページを開く
  → ユーザーが応募完了を確認
  → 応募履歴・当選履歴・受取状況を管理
```

### 1.1 最優先の完成条件

- Androidの画面端の戻るジェスチャー、3ボタンナビゲーションの戻る、画面内の戻るを自然に使える。
- 正常時の戻るで入力内容を失わない。下書き・スクロール位置・検索条件を復元できる。
- 登録、保存、編集、共有取込、通知、URL起動、当選登録、バックアップ復元まで実動する。見た目だけのボタンを残さない。
- URLを開いた事実と、実際に応募した事実を混同しない。
- 年のない日付、OCRの文字、Webページからの抽出結果を「確認済みの事実」にしない。
- 締切になっても結果待ちの履歴を消さず、落選に自動変更しない。
- 通知の制限・停止状態をユーザーに見えるようにし、「必ず定刻に届く」と表示しない。

### 1.2 配布・運用の前提

アプリ仮称は「懸賞Pocket」。applicationIdの初期案は `jp.kenshopocket.app` とし、初回配布後は変更しない。名称は仮称であり、商標やストア名の利用可能性を確認済みという意味ではない。既存リポジトリにapplicationIdがある場合は既存を優先する。

Android APKを第一対象とする。iOSネイティブ、Web/PWA、GASへの同時展開はこのアプリのv1対象外。利用者アカウント、独自サーバー、クラウドAI APIキーを要求しない。主データは端末内に保存する。

独自サーバーや有料AI APIを使わない構成であり、それらの継続課金を前提としない。通信料、開発環境、配布方法などに関する費用まで無条件にゼロと保証するものではない。

### 2.1 v1に入れないもの

完全自動応募、CAPTCHA回避、ログイン代行、XやLINEの画面自動操作、LINEトークや他アプリ通知の常時読取、当選メールの自動取得、懸賞サイトの常時巡回、複数アカウント応募、クラウド同期、課金・広告、当選確率の予測。

これらの将来機能を、押しても動かないメニューとして先に置かない。専用の外部連携や規約確認が必要な内容は、後の別開発として扱う。

初期の対応下限はminSdk 26。compileSdk／targetSdkの実装基準は36以上の安定版とし、開発開始時にSDK・AGP・Kotlin・Composeの公式互換情報を確認して組合せを固定する。「最新」を動的に指定してはならない。プレビュー版やalpha版を安易に採用しない。

各ライブラリの確定バージョン、JDK、SDK、AGP、Gradle、採用理由、確認日を `docs/BUILD_ENVIRONMENT.md` に実装時に記録する。既存プロジェクトなら互換性を保って変更を最小化する。

独立したアプリであるため、最初は `:app` の単一Gradleモジュール＋機能別パッケージでよい。巨大なMainActivityや1ファイルに全処理を詰め込む実装は不可。単純な手動DIを基本とし、既存構成がある場合のみそれを継承する。

## 4. 画面構成

常設の下部ナビゲーションは4つ: `今日 / 一覧 / 当選 / その他`。

```text
今日
 ├─ 本日締切・締切接近
 ├─ 今日応募できるもの
 ├─ 応募完了の確認待ち
 └─ 賞品の手続／受取期限
一覧
 ├─ 検索・フィルター・並び替え
 ├─ 懸賞詳細 → 編集／応募履歴／関連URL／添付画像
 └─ カレンダー
当選
 ├─ 当選一覧・未受取フィルター
 └─ 当選詳細 → 編集／受取記録／期限
その他
 ├─ 応募履歴・集計
 ├─ 下書き・要確認
 ├─ 通知設定・通知診断
 ├─ タグ管理
 ├─ バックアップ／復元／CSV
 ├─ アーカイブ・ゴミ箱
 └─ 表示設定・使い方・プライバシー・ライセンス
```

追加FABは「今日」「一覧」で表示する。開いたボトムシートに `文章を貼り付け / 画像から / 撮影 / 手動入力` を配置する。写真ライブラリやカメラが使えなくても他の登録方法は使える。

共有取込は専用ShareImportActivityを入口としてよい。同じ取込コンポーネントを再利用し、保存後は「保存して戻る」で共有元へ戻る。送信元のタスク構成によって戻り先が異なる場合はOSのスタックに従い、LINEアプリを無条件に再起動しない。

## 5. 画面別の詳細

### 5.1 今日

上部は日付と「本日未応募」「締切接近」「受取要対応」の3件数まで。大きい数字を過剰に並べない。通知が無効なら控えめな警告バーを表示し、設定へ移動できる。

表示順位は、期限が迫る賞品手続、本日締切、今日の未応募、応募完了確認待ち、その他の締切接近。各区分は空なら見出しごと省略する。全体が空なら「今日の対象はありません」と登録ボタンを表示する。

同じ懸賞が複数条件に該当するときは優先区分に1回だけ出し、複数のバッジで情報を示す。表示中に時間が経過した場合とアプリ復帰時に判定を更新する。

### 5.2 懸賞カード

基本はスマートフォンで1列。タイトルと締切を読みやすくし、情報量を理由に文字を極端に小さくしない。幅600dp以上では2列化してよい。

```text
飲料キャンペーンA                  ☆
9/27(日) 締切・時刻未確認
毎日1回 / 今日は未応募

[ 応募ページへ ]          [ ⋯ ]
```

「応募ページへ」は確認済みの有効な応募URLがある通常ケースで、1タップで起動する。カード本体は詳細を開く。カード全体のクリック領域とボタンを競合させない。

毎日タイプの応募済み状態は「今日は応募済み」。1回タイプは「応募済み」。リンク起動だけのときは「応募完了の確認待ち」。これらを同じ色だけで表現しない。

時刻が不明なのに「23:59締切」と表示しない。URL未設定なら「URLを追加」。終了済みでも詳細から「ページを確認」は利用できる。

### 5.3 登録・編集

最初に見せるのは名前、応募URL、締切、応募周期、通知。主催者、賞品、条件、タグ、メモ、関連URL、画像は折りたたみで配置する。

締切は「未設定」「日付のみ」「日付＋時刻」を切り替える。入力内容から日付＋時刻への自動昇格をしない。年は必ず表示する。

保存は下部に固定し、IME・システムジェスチャー領域と重ならない。検証エラーは対象欄の直下へ表示してフォーカスし、全画面の警告だけで済ませない。

正式保存前の変更はDraftに保存する。既存Campaign本体は「保存」を押すまで書き換えない。戻った場合は下書きとして復帰可能にする。下書き保存に失敗した場合は、成功表示をせず、再試行／コピー／破棄して戻るを提示する。

### 5.4 詳細

タイトル、締切、状態、応募ページへの大きなボタンを上部で確認できる。以下は条件、通知、応募履歴、当選、関連URL、画像、原文の折りたたみセクション。

複数URLのうち1つを主応募URLに指定する。他は「公式案内」「結果確認」「賞品引換」「その他」等のラベルを付ける。URLを削除・変更しても過去の応募時点URLは履歴のスナップショットに残す。

### 5.5 カレンダー

月カレンダーと選択日の対象一覧を同じ画面に置く。点だけでは内容が伝わらないため、選択した日のリストを必須とする。

締切、手続／受取期限、毎日の応募対象を種類で切替。毎日応募の予定を月全体に大量のイベントとして展開して読みづらくしない。「今日へ」ボタンを設ける。

### 5.6 当選

「すべて／手続き必要／受取待ち／受取済み」のフィルター。商品名、当選日、期限、受取状態を優先表示する。写真や評価額は副情報。

登録済み懸賞からの当選登録に加え、「過去の当選だけを記録」も可能とする。過去の当選のために架空の応募履歴を自動生成しない。

### 5.7 その他・設定

表示設定、通知、履歴、バックアップ等をカテゴリ分けする。運用に必須の診断と復元を深い階層に隠さない。「テスト通知」「次回通知予定」「最後のバックアップ日時」を表示する。

## 6. 操作性・戻る・状態保持

詳細な契約は `UX_NAVIGATION.md` を必ず実装する。

要点は、標準の戻るジェスチャーを独自のスワイプで置き換えないこと、戻り途中のキャンセルで保存・削除・遷移を確定しないこと、ホームの戻るを無条件に奪わないことである。[S01]

操作対象は48dp以上、主要ボタンは高さ52〜56dpを目安とする。本文16sp、補足14spを初期値とし、200%の文字拡大でも情報が読めるレイアウトへ再配置する。これは本アプリの設計値であり、48dpの下限はAndroid公式アクセシビリティ指針に合わせる。[S02]

## 7. 取り込み・解析

### 7.1 共通方針

抽出は「候補生成」であり、登録前にプレビューを挟む。文章共有やURLを受け取った瞬間に通信を始めたり、複数の応募ページを勝手に開いたりしない。

元の文章、受取日時、取得方法、OCR由来かどうかを保存する。画面の原文表示は折りたたみ。端末内の通常検索に原文を含めるかは設定可能とし、ログ出力には原文を出さない。

処理の順序:

```text
入力を一時保存 → 文字列の正規化 → URL候補検出
→ 見出し・空行・隣接行からブロック分割
→ 日付／時刻／周期／終了表現の候補生成
→ 重複候補検出 → 編集可能なプレビュー → 選択分を一括保存
```

### 7.2 文章の正規化

原文は変えず、解析用コピーを作る。改行を統一し、全角数字・全角スラッシュなどの扱いを限定する。URLのパスやクエリ全体にNFKCを適用して署名や大文字小文字を壊さない。

URL末尾の日本語の句読点や括弧は候補抽出時に切り分ける。本文内の角括弧等を一律削除しない。URL候補の根拠となる文字位置を保存して修正しやすくする。

### 7.3 複数懸賞の分割

1件につき「名前＋近接するURL＋近接する日付」を基本とする。1URL＝必ず1懸賞とは限らない。1つのブロックに複数URLがある場合は、関連URLとしてまとめた候補も示せるようにする。

日付を隣の懸賞へ勝手に結びつけない。名前や日付の関連付けが不明なら未設定として要確認にする。LINE等のリンクプレビューに同じURLが再出現した場合は候補内でまとめ、件数を水増ししない。

「抽選は終了」「ポイントはもらえる」のように特典と抽選期間が異なる文を、現在応募できる懸賞と自動判定しない。`ENDED_MENTION` と `BENEFIT_TYPE_AMBIGUOUS` を表示し、抽選／ポイント等の目的を確認させる。

### 7.4 年・日付・時刻の推定

- `2026/11/30`、`2026年11月30日`、`11/30`、`11月30日`、`9:59`、`9時59分`に対応する。
- 年がない場合、候補の年と `YEAR_MISSING` を付ける。現在日付から近い日を候補にしてもよいが、確認前に確定しない。
- 候補表示は基準日の前年・当年・翌年の有効な日付から、日数差の絶対値が小さいものを第一候補とする。同距離なら未来側を優先。古い告知である可能性は残る。
- 「1/10」を自動的に翌年の確定締切にしない。年・日付の明示確認が必要。
- 過去の日付は「終了済みの可能性」と表示し、無断で翌年に変えない。
- `9/31`等の不正な日付を10/1へ丸めない。候補を未確定にして修正させる。
- 「今日」「明日」は共有された原文が書かれた日時を確定できない場合があるため、候補扱い。スクリーンショット内の「今日」表示だけでは確定不可。
- 期間の開始・終了・発表・引換等が混在したら用途を分ける。「発表10/1」を応募締切にしない。
- 原文に曜日があり、年候補と不一致なら警告する。端末の現在年へ強制変換しない。

プレビューでは推定値に「候補」のラベルを付ける。年が欠けるなどの重大な曖昧さがある行は、明示確認するか「締切未設定で保存」を選ぶまで締切通知の対象にしない。

### 7.5 URLの扱い

`http`／`https`のみ通常の登録対象とする。スキームのないURLらしい文字列には `https://` を候補として付け、`SCHEME_ADDED` を表示する。

OCRから読み取ったURLは `OCR_URL_REVIEW` を付ける。`0/O`、`1/l/I`、大文字小文字、末尾の欠損をアプリが想像して書き換えない。改行で切れたURLは結合候補と根拠を示し、確定前にユーザー確認を求める。

開くURLと重複判定用キーを分ける。クエリ、トークン、フラグメントを勝手に削ったURLで応募させない。完全一致の重複は強く警告し、UTM等を除く類似判定は弱い候補に留める。異なるキャンペーンが同じURLを再利用する可能性があるため、重複候補を自動削除しない。

`javascript:`、`file:`、`content:`、任意の `intent:` URI、userinfo付きURLは応募リンクとして拒否する。`http`リンクには警告し、明示許可後に外部ブラウザだけで開く。内部のページ情報取得はHTTPSのみ。

### 7.6 画像

共有と画像選択はJPEG／PNG／WebPを初期対象とする。1回10枚、1枚20MBを設計上限とし、超過時は対象を明示する。全件を黙って切り捨てない。極端な画素数はデコード前にチェックし、縮小読込する。

画像は内部領域へコピーしてから処理する。外部URIの一時権限が切れても保存済み画像を見られるようにする。回転、画像プレビュー、再読取、画像の差替えを用意する。画像原本は削除しない。

OCRは日本語bundledモデルで端末内実行する。モデル同梱方式は初回のモデル取得待ちを避けるために選ぶ。認識結果の正確性は保証せず、文章の貼り付けより誤りやすいURL・数字を確認画面で目立たせる。[S06]

撮影は外部カメラアプリ＋FileProviderによる保存先指定を基本とする。カメラアプリがない場合は画像選択へ案内する。背景でのカメラ起動はしない。

### 7.7 ページ情報取得

ユーザーが「ページ情報を取得」を押した場合のみ実行する。取得前に送信先ドメインを示す。候補タイトルはHTML title／OG title、期限候補は本文の明示的な表現だけを対象とし、利用者の確定入力を上書きしない。

HTTP成功、リンク到達、主催者の正当性、応募資格、開催中であることは別の概念。「接続できた＝安全・公式・応募可能」と表示しない。状態は「未確認／取得成功／認証が必要／取得できず／要確認」とし、確認日時を残す。

ログイン、JavaScript依存、アクセス拒否では無理に取得しない。通常のブラウザでの確認と手入力を代替にする。自動リトライ巡回はしない。

通信は接続5秒／全体15秒／最大3MB／最大5リダイレクトを設計上限とする。各遷移でHTTPS、ホスト、解決先IPを検査し、localhost、ループバック、プライベート／リンクローカル／予約アドレス等へのアクセスを拒否する。DNS解決と接続先の検査を結びつけ、リダイレクトで検査を迂回させない。実装が安全にできない場合は機能を合格扱いにしない。

## 8. 締切・応募可能期間の意味

締切のデータ構造は `DATA_MODEL.md` のDeadlineValueに従う。

`DATE_TIME`は入力時刻を管理上の終了境界とする。秒が不明な入力では分の開始を保守的な通知停止基準とし、原文も表示できるようにする。公式ページの秒単位の受付を保証しない。

`DATE_ONLY`の管理上の境界は、そのタイムゾーンの翌日00:00。ただしこれは一覧整理のための仮境界であり、公式にその日一杯応募できると判断したものではない。画面・通知に「時刻未確認」を残す。`UNKNOWN`は境界なし。

`deadlineConfirmed=false`の候補日付は締切通知の計算に使用しない。日付だけをユーザーが確認した場合は日付基準の通知を使えるが、時刻不明の警告は残す。

終了状態は時刻とユーザー指定から計算する。毎日0時の更新タスクが動かなければ表示が古くなる実装にしない。終了後の登録や履歴訂正は許可し、公式応募がまだ可能かどうかとは分離する。

## 9. ワンタップ応募と応募履歴

### 9.1 応募ページを開く

標準はCustom Tabsで開く。ブラウザ機能を利用する構成とし、ログイン用の独自WebViewは作らない。Custom Tabsの提供ブラウザがない、または起動に失敗したらACTION_VIEWへフォールバックする。それも失敗したらURLコピーと設定案内を表示する。[S07]

サイトによってログイン、同意、アンケート、レシート等の操作は必要。「ワンタップ応募」は本アプリから応募先を開くまでの意味であり、外部サイトの応募完了まで保証しない。

### 9.2 起動セッション

起動前にLaunchSessionを保存する。campaignId、URLのスナップショット、launchAt、起動時の応募期間、状態を持つ。

成功した起動後にアプリが一度外へ出て、その後復帰した場合に限り確認を出す。単なる画面回転や権限ダイアログからの復帰で毎回表示しない。

```text
応募は完了しましたか？
[ 応募済みにする ] [ まだ応募していない ]
[ あとで確認 ]
```

選択は1セッションにつき冪等に処理する。あとで確認を選んだ場合、モーダルを復帰ごとに繰り返さず、今日画面の確認待ちカードに残す。

日付や週の区切りをまたいで戻った場合、どの期間で応募したかを選ばせる。ページを昨日開いたからといって昨日の応募と断定しない。

### 9.3 周期

初期の周期は `ONCE / DAILY / WEEKLY / MANUAL`。毎日・毎週は「各期間1回」の記録に対応する。1日複数口や特殊ルールはMANUALで回数を手動管理し、アプリが応募資格を断定しない。

DAILYの既定境界はAsia/Tokyoの00:00。キャンペーンごとに境界時刻を変更できる。WEEKLYは既定月曜00:00で曜日・時刻を変更可能。これは公式ルールではなく初期設定なので、登録時に確認させる。

「24時間ごと」と「日付が変われば毎日1回」は異なる。前者はv1ではMANUAL扱いとし、DAILYに自動変換しない。

応募済みにするとその期間の応募促進通知を止める。翌期間になれば、当該期間に応募記録がなければ対象に戻る。深夜ジョブによるステータスの一括リセットに依存しない。

## 10. 通知の仕様

### 10.1 初期値

- 確認済みの締切日: 3日前09:00、前日09:00、当日09:00。
- 確認済みの締切時刻がある場合: 加えて2時間前。
- DAILY: 毎日09:00。WEEKLY: 期間初日の09:00。ただし開始時刻前には通知しない。
- 賞品手続／受取期限: 前日09:00、当日09:00、時刻が分かる場合は2時間前。
- おやすみ時間: 初期状態は無効。設定時のみ適用。

全て個別にON/OFF・時刻変更可能。同時刻の同じ対象の通知はまとめる。すでに過ぎた予約は新規作成しない。07:00締切に対して当日09:00の応募促進通知を作らない。

DATE_ONLYには「締切時刻は未確認」を表示する。確定締切がない場合でも、ユーザーが独立して指定した「確認リマインダー」は作成できるが、締切通知と名前を分ける。

### 10.2 OS制約と権限

Android 13以降の通知にはPOST_NOTIFICATIONSへの対応が必要。最初の通知設定操作の際に理由を示し、拒否されてもアプリを利用可能にする。繰り返し許可ダイアログを強制しない。[S03]

通知には標準モードと「時刻を優先」モードを設ける。標準は非正確アラーム。時刻優先はユーザーが選択した場合にSCHEDULE_EXACT_ALARMの特別アクセスを確認・案内し、許可された範囲で使用する。USE_EXACT_ALARMを無条件に採用しない。[S04]

省電力制限、強制停止、電源断、通知権限、チャンネル設定等により届かない・遅れる場合がある。正確なアラームを利用しても、全状況での通知保証をしない。直前通知だけに依存させず、前日等の余裕ある通知を残す。

### 10.3 スケジューラー

Room内のReminderRuleを正とし、未来7日分のOccurrenceを決定論的に生成する。OSへは最も早い次回アラーム1つを登録する方式を基本とし、大量のアラームを無制限に予約しない。

発火時に期限・応募状態・受取状態を再確認し、該当通知をまとめて投稿する。その後、次のアラームを予約する。BroadcastReceiver内では短いローカル処理だけを行い、通信、OCR、大規模復元をしない。goAsync等の制限を守る。

標準は `setAndAllowWhileIdle`、時刻優先が利用可能なときは必要箇所で `setExactAndAllowWhileIdle` を使う。継続的なForeground Serviceや1秒ポーリングは作らない。WorkManagerは24時間程度の再整合と、必要な遅延可能処理に限定し、正確な時刻保証の代用にしない。[S04][S08]

再計算の契機は、登録・編集・応募記録変更・当選／受取変更・削除／復元・アプリ起動／復帰・端末再起動・時刻／タイムゾーン変更・パッケージ更新・関連権限変更。再起動直後に暗号化領域が読めない場合は、端末解除後に再整合する。

### 10.4 冪等性・遅延・通知抑制

Occurrenceの論理キーは、対象ID＋通知種類＋ルールの改訂＋予定日時＋応募期間。OS予約と配信の両方で重複を防ぐ。

通知投稿には安定したtag／idを使い、クラッシュ後の再試行では同じ通知を更新する。RoomトランザクションとOS通知の完全な原子性は仮定しない。履歴は「投稿処理成功」と「ユーザーが実際に見た」を区別する。

遅延発火でも管理上の終了境界を過ぎたもの、すでにその期間に応募済みのもの、受取済みの賞品は通知しない。昨日分の毎日通知は今日の応募促進として流用しない。

通知拒否時は `BLOCKED_PERMISSION`、チャンネル停止時は `BLOCKED_CHANNEL` と記録する。後で許可されても、過去の通知を大量送信せず、将来予定を再作成する。

おやすみ時間に重なる通知は次の許可時刻へ遅らせる。ただし有効期間／締切以降になる場合は配信せず `SKIPPED_QUIET_WINDOW` とし、設定プレビューに警告する。

### 10.5 通知内容と操作

ロック画面では個人情報やギフトコードを出さず、非公開表示に配慮する。通常は名前と締切、毎日タイプなら「今日は未応募」。通知本文タップは詳細画面へ移動する。

通知アクションは「応募ページへ」「1時間後」。後者が締切や当該応募期間を超える場合は設定せず理由を示す。通知上の誤タップだけで応募済みにしない。

画面起動はPendingIntent.getActivityで行い、BroadcastReceiverを経由してバックグラウンドから勝手に画面を出す構成にしない。PendingIntentは明示コンポーネント、immutable、衝突しないdata URIを使う。

## 11. 当選・受取・集計

### 11.1 当選記録

必須は賞品名と当選日。登録済み懸賞／応募履歴との関連は任意。商品写真、通知手段、メモ、個数、種類、金額換算、ポイント数、受取状況、手続期限、受取／引換期限を登録できる。

状態は `手続き前 / 手続き済み・受取待ち / 発送済み / 受取済み / 期限切れ / 辞退`。デジタル賞品は発送済みを経由せず受取済みにできる。期限切れになっても当選した事実は残す。

「5ポイント＝5円」と自動換算しない。金額が不明ならnullで保存し、0円と区別する。金額は税務計算ではなく、ユーザーが入力した参考評価額として表示する。

### 11.2 集計定義

- 応募件数: 無効化されていないEntryRecordの件数。URLを開いた回数は含めない。
- 応募した懸賞数: 上記のcampaignIdの重複を除いた件数。
- 当選応募件数: EntryRecord.resultがWINの件数。1応募で賞品が2つでも1件。
- 当選記録数: WinRecordの件数。過去の単独登録も含み、応募件数とは別指標。
- 結果判明分の当選割合: WIN件数 ÷ (WIN件数＋LOSE件数)。表示は小数1桁の四捨五入。0分母は「—」。PENDING／UNKNOWNは除外し、除外件数も示す。
- 参考評価額: 入力済み評価額だけを合計。未評価の件数を併記する。受取済み限定の集計も可能。

期間別の当選割合は応募日の同一コホートで集計する。応募日が別月なのに、今月の当選件数と今月の応募件数を割って「当選率」にしない。当選月別の受取記録とは画面を分ける。

「自分の記録における割合で、主催者の抽選確率や次回の当たりやすさを示すものではありません」と注記する。

## 12. データ保存とバックアップ

Roomのschemaを出力して管理し、既存データを残すMigrationを作る。`fallbackToDestructiveMigration` で更新時のデータを消さない。[S09]

画像はアプリ内部領域に保存する。添付元URIだけをDBに残す実装は禁止。業務データをログ、分析SDK、クラウドAIへ送らない。SDK自身のデータ取扱いは採用版の公式説明を確認してプライバシー画面に記載する。

本アプリ独自の自動クラウド同期は作らない。OSバックアップは明示的に除外設定を行い、端末メーカー等による移行動作まで一律に支配できるとは説明しない。手動バックアップの保存先はユーザーが選ぶ。[S10]

### 12.1 バックアップ形式

```text
kenshopocket-backup-YYYYMMDD-HHmm.zip
  manifest.json
  data.json
  media/<attachment-uuid>.<validated-extension>
```

manifestはschemaVersion、appVersion、exportedAt、レコード数、各ファイルサイズとSHA-256を持つ。data.jsonは懸賞、URL、タグ、応募、当選、画像参照、下書き、通知ルール、設定等の論理データを含む。

OSの権限、OS予約そのもの、配信済み判定のキャッシュ、未完了のブラウザ起動セッションは復元しない。復元後に未来の通知予定を再生成する。

v1は通常のZIP形式であり暗号化済みとは表示しない。画像やメモに個人情報が含まれる可能性を保存前に案内する。端末の共有ストレージへ無断書出しせず、Storage Access Frameworkで保存先を選ばせる。[S11]

### 12.2 復元

v1は「置換復元」のみ。差分マージを見かけだけの選択肢として置かない。内容と件数、現在データが置き換わることを表示し、明示確認後に実行する。

schema、型、必須値、外部キー、チェックサム、添付画像、容量を先に検証する。ZIP Slip、絶対パス、重複エントリー、シンボリックリンク、異常な圧縮率、未申告ファイルを拒否する。展開容量は初期上限1GB、1万ファイル。実装値をテストと一致させる。

画像は新規のステージング領域へ展開し、検証後に内部の新しいパスへ配置する。配置が完了するまでDBを書き換えない。DB更新をトランザクション化し、失敗時は既存データと画像を保持する。成功後の旧画像清掃は復元ジャーナルで再開可能にする。

### 12.3 CSV

UTF-8 BOM付きで懸賞一覧、応募履歴、当選履歴を出力する。改行・カンマ・二重引用符のエスケープ、表計算ソフトの数式注入対策を行う。原文とURL内の機密トークンは既定出力に含めず、詳細書出し時に選択させる。

## 13. セキュリティ・権限

要求する権限は、必要な通知、ネットワーク、再起動受信、ユーザーが希望する時刻優先アラームに限定する。広範なストレージ読取、連絡先、位置情報、SMS、Accessibility Service、他アプリ通知読取を追加しない。

共有入口以外の内部コンポーネントは原則非公開。共有Intentのextrasは不正型・過大入力・不存在URIを含む可能性を考慮する。画像やバックアップを信頼済み入力として扱わない。

ログからURLクエリ、原文、ギフトコード、氏名等を除外する。正式版で個人情報を含むデバッグログを出さない。自動で他アプリのクリップボードを監視せず、「貼り付け」操作時だけ読む。

## 14. 品質・エラー・性能

一覧はLazyColumnとstable keyを使用し、画像を遅延読込する。検索は軽いdebounceを入れ、DB・ファイル・OCR・通信をメインスレッドで行わない。バックアップはストリーミングで処理する。

設計上の評価用データは懸賞1,000件、応募履歴10,000件、画像1,000件。検索・表示の目標値を実装時に測定し、端末名、OS、件数を添える。未測定の数値を実績として報告しない。

低ストレージ、画像権限切れ、リンク起動失敗、OCR失敗、ネットワークなし、通知拒否、破損バックアップはすべてUIで回復方法を出す。失敗した保存を成功扱いにしない。

操作中のボタンは二重送信を防ぐが、DB側でも冪等性を保証する。読み込み中は進捗またはプレースホルダーを表示し、キャンセルが安全な処理はキャンセル可能にする。
